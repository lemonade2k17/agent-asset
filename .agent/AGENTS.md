# 全局规则

## 专业名词与英文缩写注释

每当回答中出现专业名词或专业名词的英文缩写时，必须在该词后面追加括号注释，括号内包含但不限于以下内容：

1. **英文缩写的全拼**：若该词是英文缩写，给出完整英文原文（例：`CPU` → `Central Processing Unit`）。
2. **通俗/简要概述**：用一两句通俗易懂的话解释该专业名词的含义。
3. **与其他领域相同缩写专业名词的区别**：若其他领域存在相同缩写的专业名词，须说明本处所指与它们的区别，避免混淆；若不存在同名冲突，此条可省略。
4. **常用英文名词的中文解释**：回答中出现常使用英文表达的名词时，要在该词后面加上贴近原文意义的中文解释（例：manifest（清单）、scope（作用范围））。

补充约定：

- 同一专业名词/英文缩写在一次回答中首次出现时必须注释，后续再次出现可不重复注释。
- 注释正文使用中文；全拼与缩写保留英文原文。
- 本规则适用于所有会话、所有语言、所有领域的回答。

示例：

- 缩写且存在跨领域同名：请检查服务器的 IP（Internet Protocol，互联网协议，负责为联网设备编址并路由数据包的基础通信协议；区别于内容/法律领域的 IP——Intellectual Property，知识产权，指受法律保护的创作成果）配置。
- 缩写且无同名冲突：请查看 CPU（Central Processing Unit，中央处理器，计算机中执行指令与运算的核心部件）占用率。
- 非缩写的专业名词：梯度消失（指深度神经网络训练时误差信号逐层衰减，导致浅层参数几乎无法更新的问题）。
- 常用英文名词：用 manifest（清单）里的一个字段区分即可：scope: 'session-only' | 'full'。

## 文件内容异议的处理

当用户对某个文件的内容提出异议时（包括但不限于指出错误、质疑表述、认为内容不当或不符合预期）：

- **不得在未经用户允许的情况下直接修改该文件**。即使用户的异议隐含了修改意图，也不应默认视为已获得修改授权。
- 若经分析确认异议成立，必须先给出**完整的修改建议**供用户参考，以便用户判断是否符合其意愿。修改建议应包含：
  1. **对异议的理解**：说明如何理解用户指出的问题，避免答非所问；
  2. **具体的改动内容**：拟修改的位置（文件与行号/章节）及修改前后的完整对比（原文 → 建议改为）；
  3. **修改理由**：说明该改动为何能解决用户的异议。
- 待用户明确同意（如回复"同意""按此改""可以执行"）后，再执行实际修改。
- 当用户以"怎么改呢？""如何修改？"等类似方式询问修改方法时，不应直接修改文件，而应先在对话中给出完整的修改方案和修改原因（原理），然后再询问用户是否需要修改。
- 若用户的异议存在多种理解或多种改法，应在修改建议中列出各可选项并说明差异，由用户选择。
- 若经分析认为原文并无问题（异议不成立），应向用户说明理由与依据、澄清误解，此时不强行给出修改建议。

补充约定：

- 修改建议必须完整、可直接执行，不得只描述意图而不给出具体改动内容。
- 例外：用户在提出异议的同时已明确给出修改指示并授权执行（如"把那段改成……"），可直接修改。

示例：

- 用户："这份文档第三段的描述好像不对。" → 正确做法：先回复修改建议（异议理解 + 原文与建议改文的完整对比 + 理由），询问"是否按此修改？"，经确认后再修改文件；错误做法：未经确认直接修改文件并回复"已修复"。

## C/C++ 代码开发

1. **编码标准**：代码编写遵循 MISRA C 2012 和 MISRA C++ 2012 规则。
2. **注释覆盖率**：编写代码过程中要保证注释覆盖率达到 50%。
3. **模块划分**：如果是新项目，编写代码前对项目代码进行功能模块划分。
4. **设计准则**：编写代码要遵循高内聚低耦合的准则。
5. **函数注释**：每个函数都要有 Doxygen 风格的注释，包含：
   - **函数功能简介**；
   - **函数参数**：写明输入输出方向、参数类型、参数名称、参数含义；
   - **返回值**：返回值类型、返回值名称、返回值含义。
6. **命名规则**：命名要保证名称符合其含义，特定名词可使用首字母缩写。
   - **类、结构体**：使用大驼峰命名法；
   - **函数、变量、常量**：使用小驼峰命名法；
   - **宏定义**：采用全大写加下划线的方式命名。

## 文件内容检查

当用户提出检查文件内容时：

- 只做只读检查，不得以任何方式修改被检查的文件；
- 检查完成后，按条目逐条列出检查结果。

## 任务执行监督

**触发**：需要多步推进、可能产生文件写入或对外动作、且存在被阻塞风险的任务，主模型在开始前派出一个监督 teammate。纯只读单轮问答、状态确认与格式转换不派。

**范围**：该 teammate 监督本任务涉及的全部智能体实例——主模型自身及其派出的所有子代理（含嵌套层级）；不监督与本任务无关的会话。

**手段**：teammate 不共享父级上下文，也不会自行实时观察主模型；由主模型在阶段边界向其同步任务清单、当前状态与预期产物，监督者据此判断是否存在阻塞。

**上报**：发现阻塞时写明"被什么内容阻塞"，由监督 teammate 直接告知主模型，必要时经主模型转达给受阻的执行方；阻塞未解除前不得报告任务完成。

**结束**：监督 teammate 常驻至任务结束，不自行结束；全部子任务完成或明确失败后，由主模型发送结束通知并停止后续同步。监督失败或不可用时须记录"本轮无监督"。

**周期**：不设实时轮询周期——teammate 不会自行持续观察，也读不到主模型的内部步骤；检查由主模型在阶段开始／阶段结束／子任务返回／发现阻塞时发消息触发，监督者的报告在主模型的步骤边界送达。

**成本**：监督 teammate 常驻存在，未运行时处于空闲状态、不消耗回合；每次唤醒检查都消耗 token 与上下文。同一任务只派一个，任务结束后不再唤醒。

## 选择题处理

当遇到选择题时，如果是可由主模型短时间内完成判断的内容就由主模型来判断，否则一定要调用 `closed-choice-resolver` 技能。

## 工作区改动授权

当用户进行问题咨询时，模型不能自主决定对工作区进行修改，默认只在对话里给代码/解释，不落盘，要写文件时等用户说清是否需要动手再动手。
